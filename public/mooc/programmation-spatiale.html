MODULE 0

Introduction à l'écosystème logiciel spatial

Le logiciel spatial vit sous des contraintes que peu d'autres domaines connaissent simultanément : déterminisme temps réel dur, ressources matérielles extrêmement limitées (CPU à 100 MHz, RAM en Mo), absence totale d'intervention humaine post-lancement, environnement radiatif hostile (SEU, latch-up), et exigences de certification couvrant des décennies. Cette formation part de ces contraintes pour expliquer pourquoi chaque langage occupe sa place — et non l'inverse.

0.1 La pyramide logicielle d'une mission

Une mission spatiale typique mobilise quatre couches logicielles distinctes, chacune avec ses langages et ses standards :

0.2 Pourquoi cinq langages cohabitent

L'allocation langage → couche n'est pas un héritage : elle découle de propriétés vérifiables. Le bord exige déterminisme et faible empreinte, donc C ou Ada. Le sol exige productivité et intégration, donc Java/Python/TypeScript. Les bancs exigent scripting rapide mais fiable, donc Python avec discipline. Au milieu, le C++ moderne (depuis C++14/17) gagne du terrain pour le bord non critique parce qu'il combine zéro-coût des abstractions et expressivité.

0.3 Les contraintes qui structurent tout

  • Déterminisme temporel. Toute opération critique doit s'exécuter en worst-case execution time (WCET) borné et démontrable. Cela exclut allocation dynamique, récursion non bornée, et la plupart des constructions modernes.
  • Pas de couches inutilisées. Le standard DO-178C exige la traçabilité totale : si une ligne de code n'est pas couverte par un test lié à une exigence, elle ne doit pas exister.
  • Tolérance aux défauts. Architectures duplex/triplex, watchdog, mode safe, recovery — chaque erreur doit avoir un comportement défini.
  • Validation par couches. Tests unitaires (TU) → tests d'intégration logicielle (TIL) → tests sur banc SVF (Software Validation Facility) → SCOE (Special Check-Out Equipment) → tests d'intégration satellite.
  • Durabilité. Sentinel-1A vole depuis 2014, Voyager-1 depuis 1977. Les langages choisis doivent rester maintenables sur des décennies.
À retenir avant d'aller plus loin

Le logiciel spatial n'est pas du logiciel embarqué « plus dur ». C'est une discipline d'ingénierie où le code n'est qu'un des artefacts d'un dossier de certification. Comprendre les processus (ECSS, DO-178C, IVV) est aussi important que maîtriser les langages.

Exercice 0.2Lecture de criticité

On dit qu'un logiciel est de criticité ECSS catégorie A. Que cela signifie-t-il concrètement en termes de (a) conséquence d'une défaillance, (b) processus de développement requis, (c) effort de vérification ?

Catégorie A (ECSS-Q-ST-80C) : défaillance entraînant la perte de la mission ou pire (perte de vie humaine pour missions habitées). Processus : architecture détaillée documentée, codage selon règles strictes (subset langage : Ravenscar pour Ada, MISRA pour C), revues croisées indépendantes, couverture de test MC/DC (Modified Condition / Decision Coverage) à 100 %. Vérification : équipe IVV indépendante de l'équipe développement, traçabilité bidirectionnelle exigences ↔ code ↔ tests, analyse statique WCET, fault injection. À comparer avec catégorie D (pas d'impact mission) où une couverture branches simple suffit.

Architecture des systèmes spatiaux

Comprendre où le logiciel s'insère dans un système spatial est un préalable indispensable. Ce module présente les architectures bord et sol, le cycle TM/TC, les modes de fonctionnement, le FDIR et le concept de cyclique majeur — vocabulaire et briques qu'on retrouve dans tout entretien et tout dossier technique.

Composants bord clés

  • OBC (On-Board Computer). Processeur durci radiations, typiquement LEON3/LEON4 (SPARC V8) ou GR740, parfois PowerPC RAD750. 50–250 MHz, 4–256 Mo RAM ECC.
  • Bus de données. MIL-STD-1553B (héritage, robuste, 1 Mbit/s), SpaceWire (200 Mbit/s, IEEE 1355), CAN (faible coût), TTEthernet ou SpaceFibre pour les missions récentes.
  • RTOS. RTEMS (open source, dominant ESA), VxWorks (NASA, beaucoup d'héritage), bare-metal pour très petites missions.
  • Datation. CUC ou CDS (CCSDS Unsegmented/Day-segmented Code), synchronisé GNSS ou par TC depuis le sol.

1.2 Le cycle TM/TC

La quasi-totalité des interactions sol↔bord transitent par deux flux symétriques : télécommandes (TC) du sol vers le bord et télémétries (TM) du bord vers le sol. Tout est encapsulé en paquets CCSDS.

   PAQUET CCSDS (Space Packet, CCSDS 133.0-B-2)
   ┌────────────────────────────────────────────────────────────┐
   │ Primary Header (6 octets)                                   │
   │  Version│Type│Sec.HdrFlag│   APID  │SeqFlags│SeqCount│Len  │
   │   3 b   │1 b │   1 b     │  11 b   │  2 b   │ 14 b   │ 16 b│
   ├────────────────────────────────────────────────────────────┤
   │ Secondary Header (PUS, ECSS-E-ST-70-41C) — Service/Subservice│
   ├────────────────────────────────────────────────────────────┤
   │ Application Data (paramètres TC ou champs TM)              │
   ├────────────────────────────────────────────────────────────┤
   │ Packet Error Control (CRC-16, optionnel)                   │
   └────────────────────────────────────────────────────────────┘

Les PUS Services (Packet Utilization Standard, ECSS-E-ST-70-41C) normalisent les services applicatifs sur le paquet CCSDS : Service 1 (vérification TC), Service 3 (housekeeping), Service 5 (événements), Service 8 (fonctions), Service 13 (large data transfer), Service 17 (test), Service 19 (event-action), Service 200+ privés.

Pratique IVV

Lors d'un test sur banc, tu envoies une TC PUS(8,1) « Perform Function » avec un identifiant de fonction, le bord exécute, puis remonte un PUS(1,7) « Completion of Execution » à recevoir dans la fenêtre temporelle attendue. Toute la chaîne d'IVV s'écrit ainsi.

1.3 Modes opérationnels & FDIR

Un satellite vit dans un automate fini de modes, chaque mode définissant un sous-ensemble de comportements autorisés et de surveillances actives.

                  ┌──────►│   BOOT      │
                  │       │ (ROM init)  │
                  │       └──────┬──────┘
                  │              │
                  │       ┌──────▼──────┐         ┌─────────────┐
                  │       │  STANDBY    │────────►│  NOMINAL    │
                  │       │ (post-boot) │         │ (ops normal)│
                  │       └──────┬──────┘         └──────┬──────┘
                  │              │                       │
                  │              │   anomalie            │ FDIR détecte
                  │              ▼                       ▼

                  └───────│             SAFE                 │
                          │ (orientation Soleil, comms only) │
                          └─────────────────────────────────┘

FDIR (Failure Detection, Isolation and Recovery) s'organise classiquement en 5 niveaux :

  1. Niveau 0 — protections matérielles (latchup, OCP).
  2. Niveau 1 — surveillances unitaires d'équipement.
  3. Niveau 2 — surveillances fonctionnelles (sous-système).
  4. Niveau 3 — surveillances système (passage en safe mode).
  5. Niveau 4 — reconfiguration matérielle (bascule sur unité redondante).

1.4 Le cyclique majeur

L'ordonnancement bord se fait souvent par cyclique exécutif (Major Cycle) : une trame temporelle fixe (souvent 1 s ou 250 ms) découpée en mini-cycles, où chaque tâche périodique reçoit une fenêtre d'exécution déterministe. C'est plus simple à certifier qu'un ordonnancement préemptif classique.

Exercice 1.1Décodage d'entête CCSDS

On reçoit le flux hexadécimal suivant représentant le primary header d'un paquet CCSDS (6 octets) :

18 0A C0 03 00 1F

Décode chaque champ et indique : version, type (TM/TC), présence secondary header, APID, flags de séquence, compteur, longueur des données.

Conversion binaire (16 bits de poids fort) :

0x180A = 0001 1000 0000 1010
         │││ │  ┌─────────────┐
         │││ └──┤    APID     │
         │└┴────┤ 10 (0x00A)  │
         │     SecHdr=1
         ├── Type=1 (TC)
         └── Version=000
  • Version : 0 (CCSDS standard).
  • Type : 1 → TC (Telecommand). 0 aurait été TM.
  • Sec. Header Flag : 1 → présence d'un secondary header (PUS).
  • APID : 0x00A = 10 (identifie l'application destinataire).
  • 0xC003 = 11 00 0000 0000 0011 → SeqFlags = 11 (paquet unique, non segmenté), SeqCount = 3.
  • 0x001F = 31 → longueur user data = 31 + 1 = 32 octets (convention CCSDS : length field = data_length − 1).

Diagnostic : c'est une TC adressée à l'app 10, paquet n°3 dans la séquence, avec 32 octets de données applicatives suivant l'entête.

Exercice 1.2Conception d'un FDIR de batterie

On veut surveiller la batterie d'un cubesat. Les seuils sont : tension nominale 3.3–4.2 V, alerte sous 3.0 V, critique sous 2.7 V. Conçois un FDIR à 2 niveaux qui :

  1. Émet un événement PUS(5) « battery low » sous 3.0 V pendant ≥ 3 cycles de 1 s.
  2. Bascule en safe mode sous 2.7 V pendant ≥ 2 cycles de 1 s.

Précise la machine à états et explique pourquoi on filtre les seuils sur plusieurs cycles.

Pourquoi filtrer. Une mesure isolée sous seuil peut résulter d'un transitoire (commutation de charge, SEU sur l'ADC). Déclencher une reconfiguration sur une mesure unique génèrerait des faux positifs catastrophiques (passage en safe pour rien = perte d'opérationnel).

state := NOMINAL
cnt_low := 0
cnt_crit := 0

// Tâche périodique 1 Hz
on_each_cycle(v_batt):
    if v_batt < 2.7:
        cnt_crit := cnt_crit + 1
        if cnt_crit >= 2 and state != SAFE:
            emit_event(PUS5_BATT_CRITICAL)
            transition_to(SAFE)
    else:
        cnt_crit := 0

    if 2.7 <= v_batt < 3.0:
        cnt_low := cnt_low + 1
        if cnt_low == 3:
            emit_event(PUS5_BATT_LOW)  // 1 seule fois
    else if v_batt >= 3.0:
        cnt_low := 0

Remarque : la sortie de safe mode n'est jamais automatique — elle est toujours commandée par TC depuis le sol, après diagnostic, pour garantir que les opérateurs reprennent la main.

MODULE 2

Python pour le spatial — automatisation, banc, mécanique orbitale

Python n'a jamais sa place à bord (sauf curiosités type Raspberry Pi sur ISS). Sa place est partout ailleurs : bancs IVV, post-traitement TM, génération de stimuli, automatisation de campagnes, calculs de mécanique orbitale, et de plus en plus de pipelines de données mission. Maîtriser Python pour le spatial, c'est maîtriser un sous-ensemble discipliné et des bibliothèques précises.

2.1 Sous-ensemble & bonnes pratiques IVV

  • Typage statique systématique. Type hints partout, contrôle avec mypy --strict. Le « duck typing » est interdit en IVV : un test doit échouer à la compilation si une signature change.
  • Structures immuables. @dataclass(frozen=True), NamedTuple, ou Pydantic. Les paramètres de test ne doivent pas muter pendant l'exécution.
  • Logging structuré. logging avec niveau et timestamp, jamais print(). Tous les logs doivent être horodatés à la milliseconde.
  • Pas de globales mutables. Passage explicite par dépendance, configuration par fichier YAML/TOML.
  • Reproductibilité. random.seed() fixé, environnement figé via poetry.lock ou uv.

2.3 Exemple — Décodeur de paquets TM PUS(3,25)

Le service PUS 3.25 est le rapport de housekeeping cyclique : chaque paquet contient un set défini de paramètres bord. Voici un décodeur typique d'EGSE :

from dataclasses import dataclass
from typing import Sequence
import struct
import logging

log = logging.getLogger(__name__)


@dataclass(frozen=True)
class PusHeader:
    """Représentation immuable d'un entête CCSDS + secondary PUS."""
    apid: int
    seq_count: int
    pus_service: int
    pus_subservice: int
    timestamp_cuc: float  # secondes depuis epoch mission


@dataclass(frozen=True)
class HousekeepingReport:
    header: PusHeader
    sid: int                      # Structure ID (quel HK report)
    parameters: dict[str, float]   # nom paramètre → valeur


def decode_primary_header(buf: bytes) -> tuple[int, int, int]:
    """Retourne (apid, seq_count, data_length) depuis 6 octets CCSDS."""
    if len(buf) < 6:
        raise ValueError(f"header CCSDS < 6 octets: {len(buf)}")
    word0, word1, length = struct.unpack(">HHH", buf[:6])
    apid = word0 & 0x07FF
    seq_count = word1 & 0x3FFF
    return apid, seq_count, length + 1


def decode_pus_hk_report(
    packet: bytes,
    sid_layout: dict[int, list[tuple[str, str]]],
) -> HousekeepingReport:
    """
    Décode un PUS(3,25) housekeeping report.
    sid_layout : SID → liste ordonnée (nom_param, format_struct).
    Lève ValueError si SID inconnu ou si la trame est incomplète.
    """
    apid, seq, total_len = decode_primary_header(packet)

    # secondary header PUS : 1 oct (version+ack) + 1 service + 1 subservice + CUC 4o
    service = packet[7]
    subservice = packet[8]
    if (service, subservice) != (3, 25):
        raise ValueError(f"pas un HK report (PUS {service},{subservice})")

    cuc_seconds = struct.unpack(">I", packet[9:13])[0]
    header = PusHeader(apid, seq, service, subservice, float(cuc_seconds))

    # Charge utile : SID (2 octets) + paramètres
    sid = struct.unpack(">H", packet[13:15])[0]
    if sid not in sid_layout:
        raise ValueError(f"SID {sid} non défini dans le layout")

    cursor = 15
    params: dict[str, float] = {}
    for name, fmt in sid_layout[sid]:
        size = struct.calcsize(">" + fmt)
        value = struct.unpack(">" + fmt, packet[cursor:cursor + size])[0]
        params[name] = float(value)
        cursor += size

    log.debug("HK sid=%d, %d params à t=%.3fs", sid, len(params), cuc_seconds)
    return HousekeepingReport(header, sid, params)

Exercice 2.1Décodage CCSDS pur

Écris une fonction parse_apid(packet: bytes) -> int qui extrait l'APID d'un paquet CCSDS quelconque, lève ValueError si la trame fait moins de 6 octets, et est type-safe (mypy strict). Sans utiliser de bibliothèque externe.

import struct

def parse_apid(packet: bytes) -> int:
    """Extrait l'APID (11 bits) du Primary Header CCSDS."""
    if len(packet) < 6:
        raise ValueError(
            f"paquet CCSDS trop court : {len(packet)} octets (min 6)"
        )
    word0: int = struct.unpack(">H", packet[:2])[0]
    return word0 & 0x07FF


# Test inline
assert parse_apid(bytes.fromhex("180AC003001F")) == 10

L'annotation de retour est int, l'argument est bytes ; mypy --strict passe. Le 0x07FF masque les 11 bits APID (les 5 bits hauts portent version + type + sec-hdr-flag).

Exercice 2.2Test paramétré avec timeout

Conçois un test pytest qui envoie 50 TC NOP à un EUT et vérifie que chaque acquittement PUS(1,1) arrive en moins de 100 ms. La campagne entière doit échouer si plus de 1 acquittement dépasse le seuil. Donne aussi la stratégie de log.

import time
import logging

log = logging.getLogger(__name__)


def test_nop_acquittement_50_iters(eut):
    timeouts = []
    latences_ms = []

    for i in range(50):
        eut.flush_tm()
        t0 = time.perf_counter()
        eut.send_tc("NOP")
        ack = eut.wait_for_tm(service=1, subservice=1, timeout_ms=100)
        elapsed_ms = (time.perf_counter() - t0) * 1000.0
        latences_ms.append(elapsed_ms)

        if ack is None or elapsed_ms > 100:
            timeouts.append((i, elapsed_ms))
            log.warning("NOP #%d hors temps : %.2f ms", i, elapsed_ms)

    log.info(
        "NOP campaign : min=%.2f max=%.2f mean=%.2f ms",
        min(latences_ms), max(latences_ms),
        sum(latences_ms) / len(latences_ms),
    )

    assert len(timeouts) <= 1, (
        f"{len(timeouts)} acquittements hors délai sur 50 : {timeouts}"
    )

Logique : la latence est mesurée avec perf_counter() (monotone, haute précision). La tolérance d'1 dépassement absorbe les jitters réseau du banc. Les logs WARN trace chaque outlier, le INFO final donne les stats globales (utile pour le rapport de campagne).

Exercice 2.3Détection passage à l'éclipse

À partir d'un tableau NumPy positions_eci de shape (N,3) en km et d'une date epoch, écris une fonction in_eclipse(positions, sun_direction) -> np.ndarray qui retourne un tableau booléen indiquant si chaque position est dans l'ombre cylindrique de la Terre (modèle simplifié, sans pénombre).

Modèle géométrique : on est en éclipse cylindrique si la projection de la position sur la direction Soleil est négative (côté opposé au Soleil) et si la distance perpendiculaire à l'axe Soleil-Terre est inférieure au rayon terrestre (R⊕ ≈ 6378 km).

import numpy as np

R_EARTH_KM = 6378.0

def in_eclipse(
    positions_eci: np.ndarray,    # (N, 3) en km
    sun_direction: np.ndarray,    # (3,) unitaire
) -> np.ndarray:
    sun = sun_direction / np.linalg.norm(sun_direction)
    # Projection scalaire sur l'axe Soleil
    proj = positions_eci @ sun                  # (N,)
    # Vecteurs perpendiculaires à l'axe Soleil
    perp = positions_eci - np.outer(proj, sun)  # (N, 3)
    dist_axis = np.linalg.norm(perp, axis=1)    # (N,)
    return (proj < 0) & (dist_axis < R_EARTH_KM)

Remarque : pour une vraie analyse de bilan énergétique, il faut le modèle conique (umbra + penumbra) et la position réelle du Soleil. Ce modèle suffit pour de l'ingénierie préliminaire et beaucoup d'exercices banc.

3.1 Le sous-ensemble MISRA-C 2012

MISRA-C définit ~170 règles (Mandatory, Required, Advisory) qui éliminent les zones de comportement indéfini, dépendantes de l'implémentation, ou propices aux erreurs. Les règles emblématiques :

Allocation dynamique : la règle d'or

3.2 Pattern banc-driver : lecture SpaceWire

Voici un pattern type : un driver C qui lit un paquet entrant SpaceWire avec timeout, sans allocation dynamique, à l'épreuve de MISRA :

/* spw_rx.h */
#ifndef SPW_RX_H
#define SPW_RX_H

#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

#define SPW_MAX_PKT_SIZE 1024U

typedef enum {
    SPW_OK = 0,
    SPW_TIMEOUT,
    SPW_OVERFLOW,
    SPW_HW_ERROR,
    SPW_INVALID_ARG
} spw_status_t;

typedef struct {
    uint8_t  data[SPW_MAX_PKT_SIZE];
    uint16_t length;
    uint32_t timestamp_us;
} spw_packet_t;

spw_status_t spw_rx_blocking(uint8_t port,
                              spw_packet_t * const out,
                              uint32_t timeout_us);

#endif
/* spw_rx.c */
#include "spw_rx.h"
#include "hw_regs.h"     /* registres mappés du contrôleur SpW */
#include "clock.h"       /* clock_us_now() */

static bool port_valid(uint8_t port) {
    return (port < SPW_PORT_COUNT);
}

spw_status_t spw_rx_blocking(uint8_t port,
                              spw_packet_t * const out,
                              uint32_t timeout_us)
{
    spw_status_t status = SPW_OK;

    if ((out == NULL) || !port_valid(port)) {
        status = SPW_INVALID_ARG;
    } else {
        const uint32_t t_start = clock_us_now();
        uint16_t idx = 0U;
        bool     done = false;

        while (!done) {
            if (SPW_REG(port)->status & SPW_STS_RX_DATA) {
                if (idx >= SPW_MAX_PKT_SIZE) {
                    status = SPW_OVERFLOW;
                    done = true;
                } else {
                    out->data[idx] = SPW_REG(port)->rx_data;
                    idx++;
                }
                if (SPW_REG(port)->status & SPW_STS_RX_EOP) {
                    out->length = idx;
                    out->timestamp_us = clock_us_now();
                    done = true;
                }
            } else if ((clock_us_now() - t_start) > timeout_us) {
                status = SPW_TIMEOUT;
                done = true;
            } else if (SPW_REG(port)->status & SPW_STS_ERROR) {
                status = SPW_HW_ERROR;
                done = true;
            } else {
                /* poll continu */
            }
        }
    }

    return status;
}

Caractéristiques MISRA-friendly du code ci-dessus :

  • Pas d'allocation dynamique. Le buffer est dans la structure caller.
  • Un seul return en fin de fonction (variable status assignée puis retournée).
  • Tous les if ont une branche else explicite (règle 15.7, ici via le commentaire de poll).
  • Types fixes (uint8_t, uint16_t) plutôt que int.
  • Pointeurs const dans les paramètres pour montrer l'intention.
  • Suffixes U sur les littéraux non signés (règle 7.2).

3.3 Cyclique exécutif minimal

Voici un cyclique 100 Hz bare-metal qui ordonnance plusieurs tâches périodiques sans RTOS, dimensionnable et calculable en WCET :

/* scheduler.c — cyclique 100 Hz, 10 slots */
#include <stdint.h>
#include <stdbool.h>
#include "timer.h"

#define SLOT_COUNT 10U
#define SLOT_PERIOD_US 10000U   /* 10 ms */

typedef void (*task_fn_t)(void);

static const task_fn_t cyclic_table[SLOT_COUNT] = {
    aocs_step,        /* slot 0 : AOCS 100Hz */
    tm_collect,       /* slot 1 : collecte HK */
    aocs_step,
    tc_process,       /* slot 3 : décodage TC */
    aocs_step,
    thermal_step,     /* slot 5 : thermique 20Hz */
    aocs_step,
    fdir_check,       /* slot 7 : FDIR 20Hz */
    aocs_step,
    housekeeping_emit /* slot 9 : émission HK */
};

static volatile uint8_t slot_index = 0U;
static volatile uint32_t overruns = 0U;

void tick_isr(void) {
    const uint32_t t_start = clock_us_now();

    cyclic_table[slot_index]();

    const uint32_t elapsed = clock_us_now() - t_start;
    if (elapsed > SLOT_PERIOD_US) {
        overruns++;
        /* signaler FDIR niveau 2 */
    }

    slot_index = (uint8_t)((slot_index + 1U) % SLOT_COUNT);
}

void scheduler_start(void) {
    timer_setup_periodic(SLOT_PERIOD_US, tick_isr);
    timer_enable();
}

Chaque tâche doit avoir un WCET ≤ 10 ms démontré par analyse statique (outils type Bound-T, aiT, ou OTAWA pour LEON). La table est const, en flash, donc résistante aux SEU sur RAM.

3.4 Précautions environnement radiatif

  • ECC mémoire. RAM ECC (Hamming SECDED) corrige 1 bit, détecte 2 bits. Vérifier le compteur de corrections en HK.
  • Scrubbing. Tâche périodique qui relit toute la mémoire critique pour forcer la correction ECC avant accumulation d'erreurs.
  • Triple Modular Redundancy logicielle. Les variables critiques (mode système, compteurs) stockées 3× avec vote majoritaire à chaque lecture.
  • Watchdog. Reset hardware si le main loop ne rafraîchit pas le compteur dans le délai imparti.

Exercice 3.2Dimensionnement WCET

On veut faire tourner 4 tâches périodiques sur un LEON3 à 100 MHz : AOCS (50 Hz, WCET 4 ms), TM (10 Hz, WCET 1.5 ms), FDIR (5 Hz, WCET 2 ms), HK (1 Hz, WCET 3 ms). Détermine si l'ordonnancement cyclique avec mini-cycle de 20 ms est tenable et propose une table de 50 slots (1 seconde).

Charge CPU : 50·4 + 10·1.5 + 5·2 + 1·3 = 200 + 15 + 10 + 3 = 228 ms/s ≈ 23%. CPU largement dimensionné.

Slot WCET : aucune tâche ne dépasse 20 ms ✓.

Construction de la table. AOCS doit s'exécuter tous les 20 ms (2 slots), TM tous les 100 ms (5 slots), FDIR tous les 200 ms (10 slots), HK tous les 1000 ms (50 slots). On colle AOCS en slots pairs (0,2,4,...,48) → 25 occurrences/s, soit 25 Hz et non 50 Hz.

Pour avoir vraiment 50 Hz d'AOCS, le mini-cycle doit être 10 ms et non 20 ms. Correction : mini-cycle 10 ms, 100 slots/s.

  • AOCS : tous les 2 slots (50 Hz) → slots pairs 0..98 → 50 occurrences.
  • TM : tous les 10 slots (10 Hz) → slots 1, 11, 21, ... 91 → 10 occurrences.
  • FDIR : tous les 20 slots (5 Hz) → slots 3, 23, 43, 63, 83 → 5 occurrences.
  • HK : 1 fois → slot 5 seul.

Charge max d'un slot : AOCS (4 ms) + TM ou FDIR (1.5 ou 2 ms) = 6 ms < 10 ms ✓. Marge confortable.

Exercice 3.3Vote majoritaire avec hamming distance

Étends le TMR vu en cours pour qu'il retourne aussi un status indiquant : OK (3 copies identiques), CORRECTED (1 copie divergente, 2 identiques), DIVERGED (3 copies toutes différentes). Pourquoi cette distinction est-elle utile pour le FDIR ?

typedef enum {
    TMR_OK,
    TMR_CORRECTED,
    TMR_DIVERGED
} tmr_status_t;

static tmr_status_t tmr_read_status(const tmr_uint32_t * const v,
                                     uint32_t * const out)
{
    tmr_status_t st;
    if ((v->copy_a == v->copy_b) && (v->copy_b == v->copy_c)) {
        *out = v->copy_a;
        st = TMR_OK;
    } else if (v->copy_a == v->copy_b) {
        *out = v->copy_a;  st = TMR_CORRECTED;
    } else if (v->copy_a == v->copy_c) {
        *out = v->copy_a;  st = TMR_CORRECTED;
    } else if (v->copy_b == v->copy_c) {
        *out = v->copy_b;  st = TMR_CORRECTED;
    } else {

Le déclenchement et le seuil de réaction diffèrent : CORRECTED bénin tant que < N/heure, DIVERGED = passage immédiat en safe.

4.2 Pattern : gestion d'erreurs sans exceptions

L'idiome dominant est Result<T,E> ou std::expected (C++23) ou std::variant. Voici une implémentation portable C++17 :

#include <variant>
#include <cstdint>
#include <array>
#include <span>

enum class SpwError : uint8_t {
    Timeout, Overflow, HwError, InvalidArg
};

template<typename T>
class Result {
    std::variant<T, SpwError> v_;
public:
    constexpr Result(T value) noexcept : v_(value) {}
    constexpr Result(SpwError err) noexcept : v_(err) {}

    [[nodiscard]] constexpr bool ok() const noexcept {
        return std::holds_alternative<T>(v_);
    }
    [[nodiscard]] constexpr const T& value() const noexcept {
        return std::get<T>(v_);
    }
    [[nodiscard]] constexpr SpwError error() const noexcept {
        return std::get<SpwError>(v_);
    }
};

struct SpwPacket {
    std::array<uint8_t, 1024> data;
    uint16_t length;
    uint32_t timestamp_us;
};

[[nodiscard]] Result<SpwPacket> spw_receive(uint8_t port,
                                            uint32_t timeout_us) noexcept;

// Utilisation :
void handle() noexcept {
    auto r = spw_receive(0, 10000);
    if (!r.ok()) {
        fdir_raise_spw(r.error());
        return;
    }
    process(r.value());
}
Idiomes clés

noexcept sur toute fonction qui n'utilise pas d'exception. [[nodiscard]] pour forcer l'examen du Result. constexpr pour permettre l'évaluation à la compilation quand les arguments sont littéraux. std::array remplace toujours les VLA ou std::vector.

4.3 Machine à états avec templates

Pattern de plus en plus utilisé : une FSM zero-overhead via templates et std::variant. Exemple pour le mode satellite :

#include <variant>

struct Boot      { uint32_t ticks_since_boot; };
struct Standby   {};
struct Nominal   { uint16_t orbit_count; };
struct Safe      { uint8_t entry_reason; };

using SatMode = std::variant<Boot, Standby, Nominal, Safe>;

struct EvBootDone     {};
struct EvGoNominal    {};
struct EvAnomaly      { uint8_t reason; };
struct EvGroundResume {};

using SatEvent = std::variant<EvBootDone, EvGoNominal, EvAnomaly, EvGroundResume>;

class Fsm {
    SatMode mode_{Boot{0}};
public:
    void on_event(const SatEvent& ev) noexcept {
        std::visit([this](const auto& m, const auto& e) {
            using M = std::decay_t<decltype(m)>;
            using E = std::decay_t<decltype(e)>;
            if constexpr (std::is_same_v<M, Boot> && std::is_same_v<E, EvBootDone>) {
                mode_ = Standby{};
            } else if constexpr (std::is_same_v<M, Standby> && std::is_same_v<E, EvGoNominal>) {
                mode_ = Nominal{0};
            } else if constexpr (std::is_same_v<E, EvAnomaly>) {
                mode_ = Safe{e.reason};   // transition globale possible
            } else if constexpr (std::is_same_v<M, Safe> && std::is_same_v<E, EvGroundResume>) {
                mode_ = Standby{};
            }
        }, mode_, ev);
    }

    [[nodiscard]] uint8_t mode_id() const noexcept {
        return static_cast<uint8_t>(mode_.index());
    }
};

Avantages : vérification de toutes les transitions à la compilation (impossible d'oublier un cas), zéro allocation, taille fixe (variant = max(sizeof) des alternatives + discriminant), pas de vtable.

4.4 Sérialisation TC/TM type-safe avec concepts (C++20)

#include <span>
#include <bit>
#include <cstring>
#include <concepts>

template<typename T>
concept TriviallySerializable = std::is_trivially_copyable_v<T> &&
                              std::is_standard_layout_v<T>;

template<TriviallySerializable T>
[[nodiscard]] bool serialize_be(std::span<uint8_t> buf,
                                size_t& cursor,
                                const T& value) noexcept {
    if (cursor + sizeof(T) > buf.size()) { return false; }
    if constexpr (std::endian::native == std::endian::little) {
        T swapped = std::byteswap(value);   // C++23
        std::memcpy(buf.data() + cursor, &swapped, sizeof(T));
    } else {
        std::memcpy(buf.data() + cursor, &value, sizeof(T));
    }
    cursor += sizeof(T);
    return true;
}

Le concept TriviallySerializable empêche la compilation pour des types non plats (std::string, classes avec virtual, etc.). L'erreur survient à la compilation, pas en vol.

Exercice 4.1Réimplémenter Result sans variant

Sur certains compilateurs embarqués anciens, std::variant n'est pas disponible. Réimplémente un Result<T,E> minimal sans STL avec un type tagged union manuel. Garantis l'absence d'allocation.

template<typename T, typename E>
class Result {
    enum class Tag : uint8_t { Ok, Err };
    Tag tag_;
    union Storage {
        T value;
        E error;
        Storage() {}
        ~Storage() {}
    } st_;

public:
    Result(const T& v) : tag_(Tag::Ok)  { new(&st_.value) T(v); }
    Result(const E& e) : tag_(Tag::Err) { new(&st_.error) E(e); }

    ~Result() {
        if (tag_ == Tag::Ok)  st_.value.~T();
        else                 st_.error.~E();
    }

    bool ok()    const noexcept { return tag_ == Tag::Ok; }
    const T& value() const noexcept { return st_.value; }
    const E& error() const noexcept { return st_.error; }
};

Le new(&st_.value) T(v) est un placement new : il construit l'objet à l'emplacement mémoire fourni, sans allocation heap. Le placement new est autorisé en embarqué spatial (à différencier du new classique qui appelle malloc).

Limite : il faut aussi gérer le copy/move constructor pour éviter les UB. En production, préférer std::variant ou std::expected dès que possible.

Ada & SPARK pour le critique vol

Ada vit dans le spatial depuis Ariane 4. Sa survie à 40 ans de critiques s'explique par trois propriétés introuvables ailleurs : typage extrêmement fort avec contraintes vérifiées au runtime ou à la compile-time, profil temps réel certifié (Ravenscar) prouvant l'absence de famine et de deadlock par construction, et preuves formelles via SPARK pour les sous-systèmes les plus critiques.

5.1 Pourquoi Ada résiste

Comparons un même bug — un overflow d'index — en C, C++ et Ada : 

/* C : silencieux, UB, peut planter le satellite */
uint8_t tab[10];
tab[15] = 42;   /* compile, écrit dans la pile adjacente */
-- Ada : exception Constraint_Error à l'exécution, ou erreur à la compile si index constant
type Idx is range 0..9;
Tab : array (Idx) of Unsigned_8;
Tab (15) := 42;  -- erreur compile : 15 hors Idx

En SPARK, on va plus loin : la preuve formelle démontre statiquement qu'aucun index ne peut être hors borne, qu'aucune division par zéro ne peut survenir, qu'aucun débordement arithmétique n'est possible — sans tests, sans exécution.

5.2 Le profil Ravenscar

Ravenscar (ISO 8652:2012 Annex D.13) est un sous-ensemble du modèle de tâches Ada conçu pour la certification temps réel. Il interdit toute construction qui empêcherait une analyse d'ordonnancement par Rate Monotonic Analysis :

  • Pas de file d'attente sur les protected entries de plus d'une tâche.
  • Pas de select avec delay alternatif.
  • Pas de tâches dynamiques (toutes statiques au boot).
  • Tâches périodiques exclusivement (pas de tâches sporadiques sans relation au temps).
  • Priorités fixes, ordonnancement préemptif fixed priority.
pragma Profile (Ravenscar);
pragma Partition_Elaboration_Policy (Sequential);

with Ada.Real_Time; use Ada.Real_Time;
with Aocs;

package Aocs_Task is
   task Aocs_Cyclic with Priority => 20;
end Aocs_Task;

package body Aocs_Task is

   task body Aocs_Cyclic is
      Period : constant Time_Span := Milliseconds (10);  -- 100 Hz
      Next   : Time := Clock + Period;
   begin
      loop
         Aocs.Step;
         delay until Next;
         Next := Next + Period;
      end loop;
   end Aocs_Cyclic;

end Aocs_Task;

Ce code, avec le pragma Ravenscar, est analysable : on peut calculer si le système entier respecte ses échéances par RMA classique (Liu-Layland), et le compilateur refuse toute construction qui invaliderait cette analyse.

5.3 Contrats et preuves SPARK

SPARK est un sous-ensemble d'Ada où on ajoute des contrats (pré/post-conditions, invariants) que l'outil gnatprove démontre à la compilation. Exemple — un quaternion normalisé : 

package Quaternions with SPARK_Mode => on is

   type Real is digits 15 range -1.0E10 .. 1.0E10;

   type Quaternion is record
      W, X, Y, Z : Real;
   end record;

   function Norm_Sq (Q : Quaternion) return Real is
     (Q.W * Q.W + Q.X * Q.X + Q.Y * Q.Y + Q.Z * Q.Z)
   with Post => Norm_Sq'Result >= 0.0;

   function Is_Unit (Q : Quaternion) return Boolean is
     (abs (Norm_Sq (Q) - 1.0) < 1.0E-6);

   procedure Multiply (A, B : in Quaternion; R : out Quaternion)
   with
     Pre  => Is_Unit (A) and Is_Unit (B),
     Post => Is_Unit (R);

end Quaternions;

L'outil gnatprove tentera de démontrer mathématiquement que Multiply préserve la norme unité quand ses entrées le sont. Si ce n'est pas démontrable, soit le code est faux, soit le contrat manque d'hypothèses : le programmeur doit corriger ou raffiner.

5.4 Le tableau périodique d'un AOCS en Ada

package Aocs_Pipeline with SPARK_Mode => on is

   type Sensor_Reading is record
      Gyro       : Vector3;
      Star_Track : Quaternion;
      Mag_Field  : Vector3;
      Valid      : Boolean;
   end record;

   type Actuator_Command is record
      Torque_Wheels : Vector3;
      Torque_Mtq    : Vector3;
   end record;

   procedure Step
     (Sensors  : in     Sensor_Reading;
      State    : in out Aocs_State;
      Commands :    out Actuator_Command)
   with
     Pre  => Sensors.Valid and then Is_Unit (Sensors.Star_Track),

Écris une tâche Ravenscar qui collecte les paramètres de housekeeping toutes les 250 ms, à priorité 15, et appelle HK.Collect_And_Emit. Justifie le rythme et l'utilisation de delay until plutôt que delay.

   task Hk_Periodic with Priority => 15;
end Hk_Task;

Pourquoi delay until et pas delay ? delay 0.250 compte 250 ms après l'instant de l'instruction ; si Collect_And_Emit a pris 30 ms, la période effective est 280 ms et dérive cumulativement. delay until Next rendez-vous à un instant absolu : si Collect_And_Emit dépasse, le delay est immédiat, et la tâche reste alignée sur la base de temps. Pour du temps-réel dur, on utilise toujours delay until.

Priorité 15 : sous AOCS (20) mais au-dessus des tâches d'arrière-plan. HK doit pouvoir céder le CPU à AOCS si nécessaire ; un retard de HK est tolérable, un retard d'AOCS ne l'est pas.

Écris une fonction Saturate (X : Real; Max_Abs : Positive_Real) return Real qui sature X dans [−Max_Abs, +Max_Abs], avec un contrat SPARK prouvant que la sortie est toujours bornée.

subtype Positive_Real is Real range 0.0 .. Real'Last;

function Saturate (X : Real; Max_Abs : Positive_Real) return Real
with
   Post => Saturate'Result in -Max_Abs .. Max_Abs;

function Saturate (X : Real; Max_Abs : Positive_Real) return Real is
begin
   if X >  Max_Abs then return  Max_Abs;
   elsif X < -Max_Abs then return -Max_Abs;
   else return X;
   end if;
end Saturate;

export interface TmSample {

  quality: "OK" | "STALE" | "INVALID";
}

export function useTelemetryStream(
  parameterId: string,
  bufferSize = 3600,
): TmSample[] {
  const [samples, setSamples] = useState<TmSample[]>([]);
  const wsRef = useRef<WebSocket | null>(null);

  useEffect(() => {
    const ws = new WebSocket(`wss://mcs.example.org/tm/${parameterId}`);
    wsRef.current = ws;

    ws.onmessage = (event) => {
      const sample = JSON.parse(event.data) as TmSample;

      });
    };

    return () => ws.close();
  }, [parameterId, bufferSize]);

  return samples;
}

Exercice 6.1Hook avec reconnection automatique

Améliore le hook useTelemetryStream pour gérer la reconnexion exponentielle (1 s, 2 s, 4 s, 8 s, max 30 s) en cas de coupure WebSocket. Expose aussi un état connected: boolean au composant.

export function useTelemetryStream(
  parameterId: string,
  bufferSize = 3600,
): { samples: TmSample[]; connected: boolean } {
  const [samples, setSamples] = useState<TmSample[]>([]);
  const [connected, setConnected] = useState(false);
  const attemptRef = useRef(0);
  const wsRef = useRef<WebSocket | null>(null);
  const stoppedRef = useRef(false);

  useEffect(() => {
    stoppedRef.current = false;

    const connect = () => {
      if (stoppedRef.current) return;
      const ws = new WebSocket(`wss://mcs.example.org/tm/${parameterId}`);
      wsRef.current = ws;

      ws.onopen = () => {
        setConnected(true);
        attemptRef.current = 0;
      };

      ws.onmessage = (event) => {
        const s = JSON.parse(event.data) as TmSample;
        setSamples((prev) => {
          const next = [...prev, s];
          return next.length > bufferSize
            ? next.slice(next.length - bufferSize)
            : next;
        });
      };

      ws.onclose = () => {
        setConnected(false);
        if (stoppedRef.current) return;
        const backoff = Math.min(30000, 1000 * 2 ** attemptRef.current);
        attemptRef.current += 1;
        setTimeout(connect, backoff);
      };
    };

    connect();
    return () => {
      stoppedRef.current = true;
      wsRef.current?.close();
    };
  }, [parameterId, bufferSize]);

  return { samples, connected };
}

Le stoppedRef évite la reconnexion après démontage du composant (sinon fuite de timers). Le composant peut afficher un badge orange si !connected pour alerter l'opérateur d'une perte de flux.

Exercice 6.2API Route Next.js de TC validation

Écris une route API Next.js (App Router) qui reçoit une demande d'envoi de TC en POST, vérifie le rôle JWT, vérifie que la TC n'est pas dans la liste rouge, et la transmet au backend MCS. Retourne erreur structurée si refusée.

// app/api/tc/route.ts
import { NextRequest, NextResponse } from "next/server";
import { verifyJwt } from "@/lib/auth";

const REDLINE_TCS = new Set(["FORCE_REBOOT", "DISABLE_FDIR", "PYRO_FIRE"]);
const ROLE_RIGHTS = {
  viewer: new Set<string>(),
  operator: new Set(["PUS_NOP", "GOTO_STANDBY", "HK_REQUEST"]),
  commander: new Set(["*"]),
};

export async function POST(req: NextRequest) {
  const auth = req.headers.get("authorization") ?? "";
  const claims = await verifyJwt(auth.replace("Bearer ", ""));
  if (!claims) {
    return NextResponse.json({ error: "unauthorized" }, { status: 401 });
  }

  const body = (await req.json()) as { name: string; args?: unknown };

  if (REDLINE_TCS.has(body.name) && claims.role !== "flight_director") {
    return NextResponse.json(
      { error: "redline_requires_fd", tc: body.name },
      { status: 403 },
    );
  }

  const allowed = ROLE_RIGHTS[claims.role as keyof typeof ROLE_RIGHTS];
  if (!allowed || (!allowed.has("*") && !allowed.has(body.name))) {
    return NextResponse.json(
      { error: "forbidden_for_role", role: claims.role, tc: body.name },
      { status: 403 },
    );
  }

  const resp = await fetch(`${process.env.MCS_URL}/api/tc/submit`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ name: body.name, args: body.args, requested_by: claims.sub }),
  });

  return NextResponse.json(await resp.json(), { status: resp.status });
}

Points clés : double vérification (role et redline), backend re-valide tout (defense in depth), traçabilité via requested_by dans le payload, erreurs structurées pour l'audit.

7.2 Cas B — Détection d'éclipse et bascule batterie

Scénario. Le satellite passe en éclipse 35 min/orbite ; les panneaux solaires ne fournissent plus, le bus se rabat sur batterie. La détection doit anticiper de quelques secondes pour activer mode économie.

On combine prédiction sol (Poliastro Python) avec détection bord (mesure tension panneau + horloge mission). Le sol envoie en TC les fenêtres d'éclipse prédites pour les prochaines 24 h. Le bord les utilise comme oracle + croise avec mesures. 

# Sol — calcul des fenêtres d'éclipse 24h à venir
def compute_eclipse_windows(orbit, t_start, duration_hours=24):
    sun_dir = get_sun_direction_eci(t_start)
    samples_per_orbit = 600
    n_orbits = int(duration_hours * 3600 / orbit.period.to(u.s).value) + 1
    times = np.linspace(0, duration_hours * 3600, n_orbits * samples_per_orbit) * u.s

    positions = np.array([orbit.propagate(t).r.to(u.km).value for t in times])
    in_shadow = in_eclipse(positions, sun_dir)

    # Détection des transitions
    transitions = np.diff(in_shadow.astype(int))
    starts = np.where(transitions == 1)[0]
    ends = np.where(transitions == -1)[0]
    return list(zip(times[starts], times[ends]))

Écris l'orchestrateur Python qui implémente l'étapes 2–7 du Cas C : découpage en blocs, envoi PUS(13), gestion des retransmissions sur timeout. Limite les retransmissions à 3 par bloc.

import hashlib
import logging
from dataclasses import dataclass

log = logging.getLogger(__name__)
BLOCK_SIZE = 1024
MAX_RETRIES = 3
ACK_TIMEOUT_MS = 2000


@dataclass
class UploadResult:
    blocks_sent: int
    retries: int
    success: bool


def upload_patch(eut, patch_bytes: bytes, signature: bytes) -> UploadResult:
    total_hash = hashlib.sha256(patch_bytes).digest()
    blocks = [patch_bytes[i:i + BLOCK_SIZE]
              for i in range(0, len(patch_bytes), BLOCK_SIZE)]
    n = len(blocks)
    retries_total = 0

    # Étape 3 : First Uplink Part
    eut.send_tc_pus(13, 1, payload=struct.pack(
        ">IH32s", len(patch_bytes), n, total_hash))
    if not eut.wait_ack(timeout_ms=ACK_TIMEOUT_MS):
        return UploadResult(0, 0, False)

    # Étape 5 : Intermediate Parts (sauf dernier)
    for idx, block in enumerate(blocks[:-1]):
        for attempt in range(MAX_RETRIES + 1):
            eut.send_tc_pus(13, 2, payload=struct.pack(
                ">H", idx + 1) + block)
            if eut.wait_ack(timeout_ms=ACK_TIMEOUT_MS):
                break
            retries_total += 1
            log.warning("block %d ack lost (try %d)", idx + 1, attempt + 1)
        else:
            log.error("block %d failed after retries", idx + 1)
            return UploadResult(idx + 1, retries_total, False)

    # Étape 7 : Last Part avec signature
    eut.send_tc_pus(13, 3, payload=struct.pack(
        ">H", n) + blocks[-1] + signature)
    success = eut.wait_ack(timeout_ms=ACK_TIMEOUT_MS * 2)  # vérif + flash plus long

    log.info("upload done: %d blocks, %d retries, success=%s", n, retries_total, success)
    return UploadResult(n, retries_total, success)

Le pattern à retenir : on encapsule chaque étape critique dans une boucle for/else qui n'exécute le else que si la boucle finit sans break — idiomatique Python pour le « retry jusqu'à succès ou échec définitif ».

#include <asio.hpp>
#include <array>
#include <chrono>
#include <thread>

struct HkPayload {
    uint32_t sid;
    float batt_v;
    float batt_i;
    int16_t panel_temp_dC;
    uint8_t mode_id;
} __attribute__((packed));

size_t build_pus_3_25(std::span<uint8_t> buf,
                      uint16_t apid,
                      uint16_t& seq,
                      const HkPayload& hk) {
    // Primary header : version 0, type TM (0), sechdr=1, apid
    uint16_t word0 = static_cast<uint16_t>((1 << 11) | (apid & 0x07FF));
    uint16_t word1 = static_cast<uint16_t>((0b11 << 14) | (seq & 0x3FFF));
    uint16_t data_len = sizeof(HkPayload) + 6 - 1;  // PUS sec hdr + payload − 1

    write_be16(buf, 0, word0);
    write_be16(buf, 2, word1);
    write_be16(buf, 4, data_len);

    // PUS secondary header simplifié : version 2, service 3, subservice 25, CUC 32 bits
    buf[6] = 0x20;
    buf[7] = 3;
    buf[8] = 25;
    write_be32(buf, 9, std::chrono::duration_cast<std::chrono::seconds>(
        std::chrono::system_clock::now().time_since_epoch()).count());

    std::memcpy(buf.data() + 13, &hk, sizeof(HkPayload));
    seq = (seq + 1) & 0x3FFF;
    return 13 + sizeof(HkPayload);
}

int main() {
    asio::io_context io;
    asio::ip::tcp::acceptor acc(io, {asio::ip::tcp::v4(), 42420});
    auto sock = acc.accept();

    std::array<uint8_t, 256> buf{};
    uint16_t seq = 0;
    HkPayload hk{1, 3.85f, 0.42f, 215, 2};

    while (true) {
        hk.batt_v = 3.85f + 0.1f * std::sin(seq * 0.05f);
        auto n = build_pus_3_25(buf, 0x064, seq, hk);
        asio::write(sock, asio::buffer(buf.data(), n));
        std::this_thread::sleep_for(std::chrono::seconds(1));
    }
}

Squelette Python décodeur + serveur WebSocket :

import asyncio, struct, json
import websockets

clients = set()

async def read_bord():
    reader, _ = await asyncio.open_connection("127.0.0.1", 42420)
    while True:
        header = await reader.readexactly(6)
        length = struct.unpack(">H", header[4:6])[0] + 1
        body = await reader.readexactly(length)
        # PUS sec hdr 7 oct (version+service+subservice+CUC) puis HK payload
        sid, batt_v, batt_i, temp_dC, mode = struct.unpack(">IffhB", body[7:7+15])
        sample = {"t": int(asyncio.get_event_loop().time() * 1000),
                  "batt_v": batt_v, "batt_i": batt_i,
                  "temp_C": temp_dC * 0.1, "mode": mode}
        msg = json.dumps(sample)
        dead = []
        for ws in clients:
            try:
                await ws.send(msg)
            except:
                dead.append(ws)
        for ws in dead: clients.discard(ws)

async def ws_handler(ws):
    clients.add(ws)
    try:
        await ws.wait_closed()
    finally:
        clients.discard(ws)

async def main():
    server = await websockets.serve(ws_handler, "127.0.0.1", 8765)
    await asyncio.gather(read_bord(), server.wait_closed())

asyncio.run(main())

8.3 Questions d'entretien type

Oral10 questions techniques
  1. Différence entre PUS service 3.25 et service 3.27 ? Quand utiliser l'un plutôt que l'autre ?
  2. Comment calcules-tu le WCET d'une fonction C ? Quels outils ?
  3. Pourquoi Ada Ravenscar interdit-il les sporadic tasks sans contrainte de minimum inter-arrival time ?
  4. Comment garantis-tu qu'un patch logiciel uploadé en orbite ne va pas bricker le satellite ?
  5. Sur un MCS, pourquoi double-valider les TC critiques côté front et côté back ?
  6. Donne deux différences entre MISRA-C 2012 et JSF C++.
  7. Comment détectes-tu un SEU silencieux (qui n'a pas déclenché ECC) ?
  8. À quoi sert un major frame en cyclique exécutif ?
  9. Pourquoi l'opérateur sol ne sort-il jamais automatiquement du safe mode ?
  10. Que fait delay until qu'un simple sleep ne fait pas ?
  1. PUS(3,25) = HK report cyclique automatique (envoyé spontanément par le bord à période fixe). PUS(3,27) = HK report sur demande sol. Le premier sert le monitoring permanent, le second le diagnostic ponctuel ou les paramètres peu fréquents qu'on n'inclut pas dans le HK cyclique.
  2. Trois familles : (a) static analysis avec aiT, Bound-T, OTAWA — analyse le binaire et le modèle du processeur ; (b) measurement-based avec mesures sur cible et facteur de sécurité (souvent ×1.5–2) ; (c) hybrid qui combine analyse de chemins et mesures. En spatial certifié on exige du static avec preuve mathématique.
  3. Sans minimum inter-arrival time, on ne peut pas borner la charge CPU pire cas : RMA suppose une période minimum garantie. Ravenscar autorise les sporadic via protected entry avec pragma Implementation_Defined_Suspension, mais avec MIAT déclarée.
  4. Trois couches de protection : (a) signature cryptographique vérifiée bord avant écriture flash ; (b) écriture dans une partition secondaire, le bootloader teste la nouvelle image et reboot sur l'ancienne si le watchdog n'est pas alimenté au bout de N secondes ; (c) garde toujours une safe image en flash protégée write-once.
  5. Defense in depth. Le front empêche les clics accidentels et donne du feedback utilisateur. Mais un front compromis (XSS, dev tools) pourrait forger n'importe quelle requête : le back est la seule autorité de sécurité. Sans re-validation back, un attaquant qui prend la main sur une session passe tout.
  6. MISRA-C cible le C ISO ; JSF C++ cible le C++ (avec orientations objet, templates, RAII). MISRA est consensus industriel automobile/aéro étendu ; JSF est plus restrictif sur le C++ (interdit RTTI, multiple inheritance, certains aspects du polymorphisme).
  7. Le scrubbing périodique force la relecture donc l'éventuelle correction ECC. Pour les SEU sur données critiques non ECC, on utilise du TMR logiciel avec divergence détectée → événement FDIR.
  8. Un major frame est la période complète après laquelle le schéma d'ordonnancement se répète. Toutes les tâches périodiques ont une fréquence divisant le major frame. Cela permet une analyse exhaustive (vérifier que sur 1 hyperperiod, toutes les échéances sont tenables).
  9. Parce qu'une sortie automatique de safe sur la base de la même mesure qui n'a pas détecté le problème initial est un risque inacceptable. Le sol procède à un diagnostic complet (lecture HK historique, vérification autres sous-systèmes), corrige la cause, puis commande la sortie en connaissance de cause. C'est aussi un principe ECSS : man-in-the-loop sur les transitions critiques.
  10. sleep(t) attend t depuis l'instant d'invocation → dérive cumulative à chaque cycle si le code utile prend du temps. delay until t_absolu attend jusqu'à un instant absolu : la dérive ne s'accumule pas, et si la tâche dépasse, le delay est immédiat. Indispensable pour toute boucle périodique temps-réel.
